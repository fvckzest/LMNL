# Square evidence for the LMNL Managed Ticketing pilot

**Research date:** August 13, 2026

**Scope:** What LMNL can evidence with its own Square account for one Washington **Pilot Event**. This is technical research from Square's official documentation, not a determination that LMNL may use Square for the proposed seller/settlement model. The [pilot-boundary research in PR #14](https://github.com/fvckzest/LMNL/pull/14) makes Square's written seller-structure confirmation a no-sales gate.

## Bottom line

If the configured production token is verified to authorize LMNL's seller account, it can produce a durable, event-reconcilable record of (1) ticket payments, (2) Square processing fees and later fee adjustments, (3) refunds and their final status, (4) disputes and their financial effect, and (5) Square's payout of its own balance to LMNL's banking destination. Those records **cannot** prove that LMNL paid the **Settlement Recipient**: the Payouts API is read-only and describes transfers from the *seller's* Square account to a banking destination. The current pilot therefore needs a separate, retained bank-transfer/payment confirmation for each manual **Recipient Settlement**.

The code already attaches an LMNL request and event to Square Orders. However, it does not persist Square payment IDs, refund IDs, dispute IDs, payout IDs/entries, or Square webhook `event_id`s. It is sufficient to issue a ticket once, but not to calculate or preserve a complete event settlement ledger without an additional evidence model.

## Evidence available under LMNL's Square account

All of the following is evidence for the Square seller account authorized by the configured credential—not for a separate organizer. The source only loads opaque environment values, so before sales LMNL must retrieve and retain the production merchant/location identity and verify that the token belongs to LMNL's seller account. The Payments API says the payment goes to the account identified by the request Authorization header. [Payments API reference](https://developer.squareup.com/reference/square/payments-api), [Merchants API](https://developer.squareup.com/reference/square/merchants-api).

## Payment and order evidence for this codebase

### What the current code does well

- `api/_lib/services/event-checkout.js` creates an Order with `referenceId` = LMNL request ID and `metadata.requestId` and `metadata.eventId`, then passes the returned Order ID to `payments.create`. This makes the Square `Payment.order_id` a reliable route back to the event order.
- `api/_lib/services/checkout.js` does the same correlation for hosted Payment Links and persists `paymentLink.orderId` on the LMNL request.
- `api/_lib/services/webhook-fulfillment.js` retrieves the Order again before ticket fulfillment and prefers `metadata.eventId`; it also has a unique `tickets.square_order_id` database constraint in `sql/phase6_ticket_idempotency.sql`.
- `Payment.reference_id` is also set to the LMNL request ID for the direct card path. Square describes `reference_id` as an optional association to an entity in another system. [Payment](https://developer.squareup.com/reference/square/objects/payment)

### Gaps that matter for a Pilot Event settlement

1. The LMNL database stores Square **order** IDs on requests/tickets, but no Square **payment** ID. That means payout entries, refunds, and disputes need an API lookup to bridge `payment_id → order_id`, and an exported settlement packet cannot prove that bridge after the fact without retaining the payment snapshot/ID.
2. Event checkout and hosted checkout make a fresh random idempotency key on each request. Square requires a unique `idempotency_key` for each `CreatePayment`; reusing the same key for a genuine retry prevents another payment, whereas generating a new key after an uncertain timeout can create a second order/payment. [CreatePayment](https://developer.squareup.com/reference/square/payments-api/createpayment), [Create Order](https://developer.squareup.com/reference/square/orders-api/create-order). The pilot needs a persisted operation key per intended purchase/refund, not only a random process-local UUID.
3. The current fulfillment webhook treats an Order as fulfillable when it is `COMPLETED` or is `OPEN` with a tender. The financial settlement must instead use the linked Payment's final `COMPLETED` status and amounts. Square payment states include `APPROVED`, `PENDING`, `COMPLETED`, `CANCELED`, and `FAILED`; some methods are asynchronous. [Payment](https://developer.squareup.com/reference/square/objects/payment), [Payments webhooks](https://developer.squareup.com/docs/payments-api/webhooks).
4. The code has no refund, dispute, or payout evidence pipeline. A refunded ticket remains a ticket today; a later chargeback does not change it or produce a settlement adjustment record.
5. All event records currently expose a mutable event name and metadata. The settlement system needs immutable event ID and agreement/price/terms snapshot references so later edits cannot rewrite the historical basis.

## Webhook design and operations

Square webhooks must be treated as prompts to retrieve current Square state, not as an ordered accounting ledger.

- Subscribe to `payment.updated`, `refund.updated`, `dispute.created`, `dispute.state.updated`, `payout.sent`, `payout.paid`, and `payout.failed` at minimum. Square documents the payment, refund, dispute, and payout event families separately. [Payment webhooks](https://developer.squareup.com/docs/payments-api/webhooks), [refund.updated](https://developer.squareup.com/reference/square/webhooks/refund.updated), [Dispute webhooks](https://developer.squareup.com/reference/square/disputes-api/webhooks), [Payout webhooks](https://developer.squareup.com/reference/square/payouts-api/webhooks).
- Verify the `x-square-hmacsha256-signature` against the raw request body and exact configured notification URL with constant-time comparison. The current code has the raw-body HMAC shape, but it fails open when the secret or signature is absent, accepts legacy headers and URL variants, and compares with `===`; these are pilot-blocking limitations, not sufficient verification. [Validate the notification](https://developer.squareup.com/docs/webhooks/step3validate).
- Store Square `event_id` before/as part of processing and make it unique. Square explicitly says to use `event_id` to bypass repeated delivery. The current code deduplicates ticket fulfillment by Order ID, but it does not persist webhook `event_id`, so it cannot audit or safely deduplicate non-ticket events. [Create a notification URL](https://developer.squareup.com/docs/webhooks/step1createurl).
- Acknowledge quickly, then process durably. Square expects a timely `2xx`; if it does not receive one, it retries for up to 24 hours with exponential backoff. Event delivery order is not guaranteed. Retried delivery headers include `square-retry-number` and `square-retry-reason`. [Webhooks overview](https://developer.squareup.com/docs/webhooks/overview), [event notification format](https://developer.squareup.com/docs/webhooks/step2subscribe).
- On every received event, retrieve the authoritative resource (`GetPayment`, `GetPaymentRefund`, `GetDispute`, `GetPayout`, or Order) and append a snapshot/transition. This handles incomplete webhook payloads, late fee computation, eventual consistency, and out-of-order versions. Payment and refund list endpoints are eventually consistent; Square notes payment fee information can be added in a later `payment.updated` event. [List Payments](https://developer.squareup.com/reference/square/payments-api/ListPayments), [Payments webhooks](https://developer.squareup.com/docs/payments-api/webhooks).

## Reconciliation rules for the pilot

Use an event-level worksheet whose rows are immutable Square IDs, not dashboard totals or payment-link counts:

1. **Identify ticket transactions:** start from the event's LMNL request/order IDs, retrieve the associated Payments, and verify the Order's `metadata.eventId`. A report can also start from payout entries, but must join `payment_id → Payment.order_id → Order.metadata.eventId` before inclusion.
2. **Completed ticket payments:** include only Payments with `status = COMPLETED`; retain gross `amount_money`/`total_money`, receipt URLs, and any tax amount already present on the Square Order. A Payment can still be `COMPLETED` after a partial/full refund, so subtract completed `PaymentRefund.amount_money` (or use `Payment.refunded_money` as a cross-check). [Refund Payments](https://developer.squareup.com/docs/payments-api/refund-payments).
3. **Processing fees:** start with the per-payment `processing_fee`, then reconcile against Payout Entries. Retain `FEE` and `PROCESSING_FEE` adjustments that arrive later; do not assume an initial payment fee is the final cash-balance impact. Square specifically warns that those entry types update a previous fee. [Payouts guide](https://developer.squareup.com/docs/payouts-api/overview).
4. **Disputes:** record a dispute when opened and its payout-entry effect when it hits the balance. Only a final lost/accepted outcome belongs as an actual chargeback deduction. The statement must retain the unresolved-dispute reserve or explicitly say the Recipient Share remains recoverable under the agreement.
5. **One pilot tax setting:** before sales, record a single event-specific answer—tax applies or it does not. If tax applies, configure it as a Square Catalog/Order tax on the hosted-checkout path and verify the resulting Order total and `total_tax_money`; the current direct payment path neither adds an Order tax nor charges a computed taxed total, so it cannot be used for a taxed Pilot Event without a code change. Preserve any Square-collected tax separately from the LMNL Fee and Recipient Share. The pilot does not need a tax engine, marketplace-tax architecture, or automated filing workflow. [Order taxes](https://developer.squareup.com/docs/orders-api/apply-taxes-and-discounts).
6. **Square payout:** attach any Payout and entries that include pilot payments as bank-reconciliation evidence. Do not require a single clean payout—Square says typical payouts batch a business-day window and may include all LMNL activity. [Payouts overview](https://developer.squareup.com/docs/payouts-api/overview).
7. **Recipient Settlement:** after the event, attach the independently issued settlement statement and the manual bank-transfer proof. Its reference must be separate from Square's `payout.id`/`end_to_end_id` unless it is actually the LMNL bank deposit reference.

## Minimum pilot evidence packet

Before any sales, confirm the production merchant and location belong to LMNL and that production access can read the required scopes/resources without changing live data: `PAYMENTS_READ`, `ORDERS_READ`, `PAYOUTS_READ`, and dispute-read access as needed; write access is separately required only to create payments/refunds. Do not treat a sandbox result as production permission evidence.

For each settlement, retain:

- fixed event/agreement/terms version and event identifier;
- Square Order, Payment, Refund, Dispute, Payout, and PayoutEntry exports/snapshots keyed by their immutable Square IDs;
- the event-to-order-to-payment-to-payout-entry join table, including pagination/watermark time and API version used;
- the calculation showing gross completed payments, any tax Square collected, completed refunds, final chargebacks, all fee adjustments, the agreement-defined LMNL Fee (10% for this Pilot Event), and Recipient Share;
- Square webhook delivery/event IDs and any retry/out-of-order handling record;
- ticket issuance/check-in evidence and buyer communications needed for a dispute response; and
- the LMNL-to-Settlement-Recipient transfer approval and bank confirmation.
